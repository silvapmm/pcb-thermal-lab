# Text for the Decisions Log of `CLAUDE.md` (when the feature is adopted)

* **Memory guard** (`feature/memory-guard`, from `research/memory-guard`): one guard by estimated memory replaces `solid3d.MAX_CELLS` and `fvm.MAX_SOR_BLOCK`. The estimate is one law per model, `base + k1 t_eff^a N (N / 500 000)^(p - 1)` with t_eff = min(t, cells / t) and t = unknowns / plan cells (safety factors 1.40 FVM, 1.24 FDM, 1.30 3D solid; the Lumped and the Analytic never refuse in the measured range); the review replaced a first table of eight classes by t because it was flat in t and fell up to 1.41 times below boards of 8 and 12 copper layers, with coefficients fitted on a ladder of 145 measured points, each point run in its own process with its peak resident memory read from the kernel. The limit is a fraction of the installed memory (70 % by default, editable in Preferences); the verdict ok, slow or refuse is used by `api.simulate`, the jobs, the interface and the command line. No new dependency (os.sysconf, sysctl, /proc/meminfo, ctypes). The block SOR costs up to 75 n^2 bytes (measured), so `MAX_SOR_BLOCK = 5000` was about 1.9 GB. The animation transient kept ten LU factors (3.5 times the steady memory). Measured: the layered FVM is linear in the unknowns only for thin graphs (t up to 4.5); a six-layer plain board takes 8.8 GB per million unknowns; the cell-major numbering gave no general gain. Decided by the maintainer: <the margin, the slow mark (predicted solve time above 30 s proposed), installed against available memory and the default fraction (60 % or the minimum with the available memory proposed), the 3D ceiling (2 million proposed), the share of the limit for the SOR block (25 % proposed), cell-major numbering (not part of the guard)>.
