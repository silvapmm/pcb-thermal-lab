# How real-board import would enter the program (design, not implemented)

*Release 2.5.0, theme "real boards: import a Gerber set without blowing the memory". This is a design; both blocks of studies have run (section 7 for the first block, section 8 for the second: copper mapping, fine-copper warning, Lumped and Analytic rule, transient, time and memory) and say what they confirmed and what they changed. The earlier design documents are `research/gerber-models/INTEGRATION.md` and `research/gerber-nets/INTEGRATION.md`.*

Short answer: **a small import package with no new dependency (our own reader), an imported-copper element that hands the models face conductances, a paste-to-part step that turns paste groups into parts, a guard that estimates the memory before building, and a project-file format 2 that stores what the import understood.** The physics of the models does not change; zones keep their formula.

## 2. What does not change

* The physics of every model; `Zone.fill` and the union of zones (the evidence that a fill must keep its formula is in `gerber-models` 4.10, 4.27, 4.39); existing projects open and give bit-identical results (a project with no import takes the old code path).
* The program has no new dependency: the reader is NumPy only; gerbonara and shapely stay a test reference in the research environment.
* A part imported from the paste layer is an ordinary heater/component of the program (the worst-case convention: all the power enters the board; the junction resistance and the top path are the user's, as for a drawn part).

## 3. The project-file format 2

*Prototype: `lib/project_format.py` (pack, unpack, migration, downgrade), measured by `scripts/study_project_file.py`; the tests are in `tests/test_fine_memory_format_odb.py`.*

* **Format key.** Format 1 is `pcbthermal-project-1` (`pcbthermal/project.py`: the problem JSON plus `solver`, `view` and `app_version`); format 2 is `pcbthermal-project-2` and keeps every key of format 1 and adds one list, `imports`. **Migration 1 to 2** adds an empty list and changes the key (exact, tested); **2 to 1** is refused when the list is not empty (the copper would be lost), otherwise exact. A file with no `format` key (a plain native file) is read as format 1.
* **What an import record stores** (one per imported board): the name, the pixel of the masks, the box in the file coordinates, the settings of the import (layer roles and order, the units of the drill file, the outline choice), per copper layer its name, role and mask, the plated holes (position, diameter, via or component hole), the imported parts (reference, footprint, the paste-group box and the shape chosen), the warnings of the import, and **the source files by name, size and SHA-256 (never by path of the user's disk)**.
* **Embedded or referenced masks.** Embedded: the mask is packed (bits for binary, a byte for coverage, deflate, base64) in the record; the project is self-contained, opens on another machine and does not depend on files that may have moved or may not be redistributed. Referenced (`"embed": false`): only the roles and the file identities; the mask is redrawn from the Gerber files when the project opens, which needs them and costs the import time. **Proposed default: embedded at the pixel of the import, binary masks**; the size on seven real boards (study 4.8) is 0.02 to 0.43 MB at 0.05 mm (0.16 MB for a 4-layer 100 x 100 mm board; criterion 20 MB) and 0.04 to 0.87 MB at 0.025 mm, so **the "reference only" option is not needed for the size**; the 8-bit coverage mask costs 1.5 to 2 times the binary one after compression (not eight times), so what the 8 bits are worth against the 1 bit is decided by study 4.1 alone.
* **A program older than the change opening a format 2 file (measured).** Opening a file with `"format": "pcbthermal-project-2"` and an `imports` list in the released 2.4.5 raises no error and no message, **drops the imports, and a Save writes the project back as format 1 without them** (study 4.8; unknown keys inside `board` and inside a zone are accepted as well). So a format 2 file in an older program is a data-loss path, not only a missing layer. Options for the maintainer: (a) accept it and say so in the release notes; (b) write next to `imports` a coarse zone fallback that older programs read (a cell-sized zone per mixed cell: large, and a different physics); (c) a **different file extension or name for projects with imports**, so the older program does not offer the file in its dialogs by default (it still opens it by hand: this lowers the risk, does not remove it); (d) a patch release of 2.4.x whose `project_from_dict` refuses a `format` it does not know (it protects only the machines that install the patch). The investigation's recommendation after the measurement: **(c) plus the new version writing a visible message and a `.bak` copy of the older file when it migrates**, and (d) if the maintainer wants the old versions covered; (a) alone is not recommended now that the loss on Save is known.

  **Review: recommendation changed to (e).** (e) **A layout that the older readers cannot open.** `project_from_dict` of 2.4.x reads `data["board"]` first; a format 2 file whose problem sits under a key (`{"format": "pcbthermal-project-2", "project": {...the format 1 content...}, "imports": [...]}`) is **refused** by 2.4.5 with `KeyError: 'board'`, which the application shows as "Cannot open file" and the command line as an error, so nothing is opened and nothing can be saved over it (verified on the released tag by the review and printed by `study_project_file.py`). It protects **every installed 2.4.x** without any patch, which (d) cannot do (a patch protects only the machines that install it, and a user who updates would install 2.5.0 anyway). With it: write format 2 **only when the project has imports** (a project without imports stays format 1 and opens everywhere, as today); before the first save in format 2 over a file that was format 1, keep a `.bak` copy; the release notes and the user guide say that projects with imported boards need 2.5.0 or later; and the 2.5.0 reader **refuses any format newer than the ones it knows**, with a message naming the version that wrote the file (`app_version` is already written), so the next format change does not repeat the problem. The message of 2.4.x is terse ("'board'"); a clearer one would need a patch, which is not worth a release on its own. (c), a different extension, is not needed then (it would split the file dialogs and the documents). **A 2.4.6 patch is not justified for this question**: no format 2 file exists yet (no released program writes one), the nested layout closes the loss for the older versions as they are, and 2.4.6 would only make sense if the maintainer prefers the flat layout of the prototype. The prototype `lib/project_format.py` keeps the flat layout; the nested one is a small change at implementation.

## 4. Memory (what the guard needs from the studies)

* The unknowns of an imported board are `layers x cells` for the face network; the program's own count with the laminate rule is ragged (`fvm.unknowns`, 1.75 times larger on the four-layer boards measured). **Measured (section 8, nine cases)**: the research pipeline peaked at 9.4 KB per unknown of the faces above 100 000 unknowns (20 % scatter; 5.5 KB on the program's count), and above 150 000 unknowns the whole peak is within the safety factor 1.40 of the FVM law of `research/memory-guard` (ratio 1.06 at 593 000 unknowns, 1.07 to 1.4 between 150 000 and 375 000); below 100 000 unknowns the raster and fixed costs make it up to 1.7 times the law.
* The mask itself is memory too, and it is the larger part of an import's peak: about **55 bytes per pixel per copper layer** measured (import phase alone 1.94 GB on ISASTM at pixel 0.035 mm, four layers), with pixel = cell / 10 about 5.5 KB per cell and layer, comparable to the solve itself; the importer must draw layer by layer and keep bytes, not float64, and a windowed or streamed import would remove most of it. A whole board at 0.25 mm was not run (about 6 GB for ISASTM by these figures).
* The guard refuses **before** drawing: pixel, cell and layers give the estimate; the message says which cell fits.
* **Measured in the first block**: the research importer holding every layer's binary and coverage arrays together reached about 6.5 GB for the seven boards at three pixels (the largest case is probably CO60 at 0.025 mm: 285 x 95 mm, 43 million pixels per layer); the second block's raster figure (55 bytes per pixel per layer) agrees. The guard for the *mask* is needed besides the one for the unknowns.

## 5. Risks and limits (stated, not hidden)

* **Fine copper**: with the flow-based faces the cell model is within 5.5 % of the pixel reference on all 108 one-sheet cases (0.5, 1.0 and 2.0 mm cells), and no indicator of fine copper predicts the few cases above 5 % (section 8); with the arithmetic fill it is 10 to 30 % cool on real copper whatever the indicators say. Isolated diagonal copper on a coarse grid is the largest residual error known and is not fixed by the faces (the diagonal gate failed its held-out test in `gerber-models` 4.50).
* **Lumped and Analytic** are 16 % and 26 % below the FVM on the rectangle board and 1 to 16 % cool on imported windows; on imports they always warn (4.5).
* **No measurement**: no physical board exists yet; every accuracy statement is against another model of the same physics. The documents must say so.
* **A part from the paste is a footprint, not a package**: the junction resistance, the top path and the power are the user's; a part with no paste opening (through-hole, glued) is not found; placement origins differ between tools (the registration finds the offset from the data and reports how many parts matched).
* **Copper thickness and stack-up** are not in the Gerber copper files: the program's stack-up (typical templates, the Gerber job file's board thickness and layer count when present) supplies them; the user confirms.
* **Plated holes become vias** (open barrels of the hole's diameter; a component lead is not modelled); a via and a component hole are told apart by the aperture function when written and by a diameter filter and a preview when not.
* **Licences of user files**: nothing of a third party's board is stored by the program except what the user's project embeds (the user's own files); the research folder stores none.
* **Placement frames**: on the five boards that name their parts the placement frame equals the Gerber frame (offset below 3 micrometres, no sign flips) except that **KiCad's combined position file mirrors X on the bottom side**; the vote registration on unnamed proximity groups returned wrong offsets on two of five boards, so it must not be the default. Without names (RP2040, CO60, vstcm) the match is approximate and the program says so.
* **A line thinner than the pixel is silently lost**: a 0.01 mm line at a 0.05 mm pixel with supersampling 2 gave an area of 0 (exact 0.400 mm2); the importer must derive the pixel from the thinnest feature of the layer or warn.
* **The laminate rule and the faces** (review, README 9.2): every comparison of the mappings ran with the laminate rule off on both sides; on two-layer boards the rule moves the result by up to 7.6 points. Until the faces are measured with the rule on against an independent 3D reference, their accuracy on two-layer boards is not known.
* **Third-party renders** (review): a figure that draws a downloaded board keeps that board's licence and is noted in `research/README.md` (figure 8 was redrawn from a synthetic file of our own); the program's own screenshots and documents use our boards only.
* **Specification only partly read**: the component-layer, `.C`/`.Cxxx` attribute and `AB` overview sections of revision 2026.05 were read (README section 8); the attribute dictionary, the aperture-block usage and transformation chapters and the file functions of paste layers were not, and must be read before the refusal of `AB`, `LM`, `LR`, `LS` is lifted.

1. ~~The default mapping~~ answered by section 8: the flow-based faces; whether to keep an optional switch to the arithmetic fill in Preferences is left (recommended: no switch, a project setting only for comparison).

8. Whether the research code is moved into `pcbthermal/` as it is (the reader is validated; the face network, the paste and the placement code are prototypes with tests but no run).
9. (Review) Figure 8 redrawn from a synthetic paste file (done; the GPL-3.0 render is removed).
10. (Review) The layout of format 2 (section 3, option (e) recommended) and whether a 2.4.6 patch is wanted at all (not recommended).
11. (Review of README 10) **The default mapping of an import with the 2.4.5 rule: the flow-based faces on the reduced sheet.** Recommendation: **adopt** (README 10.5: better than the fill in 41 of 42 real window-cells on the mapping alone, 21 of 21 windows against the 3D reference). Measured impact: against the fill the heater rise of a real window is warmer on average by 2.2 to 3.8 % of the rise on two layers (cells 0.6 / 1.2 mm) and 1.5 to 1.7 % on four; as a share of the rise above the board mean the error falls from 31 to 39 % to 11 to 17 %.
12. 13. (Review of README 10) **The network's own error with the rule on two-layer boards** (the program at the pixel is 1.6 % of the rise cool on average against the 3D reference, up to 3.9 %; 4 / 8 / 16 sub-gaps give -3.90 / -2.25 / -1.41 % on the islands board). Not an import question: it holds for every mapping and for zones, and belongs to the laminate rule (`laminate.N_MAX = 4`). Recommendation: record it as a limit in the documents of the import and of the rule; a larger `N_MAX` for thick two-layer gaps is a separate study (cost about 1.0 to 2.5 times the unknowns per doubling, `research/laminate-nodes`), not part of 2.5.0 unless the maintainer wants it.

## 9. Scope and branches (review)

**Scope proposed for 2.5.0:** Gerber copper, Excellon drills (plated holes as vias) and the outline with our reader; the imported-copper element with the copper capacity; parts from the paste layer by `TO.C`, the placement file matched by name, the click with a box or a hull (proximity groups as a marked fallback); the project format 2 in the nested layout; the memory guard with the import terms; the warnings (Lumped and Analytic on imports, the cell model of imported copper, a feature thinner than the sample spacing). The default mapping is the flow-based faces built on the reduced sheet of the rule (README 10 confirms them with the laminate rule on: 21 of 21 real windows closer than the fill fraction; the faces of 4.1 as they stand are not usable on the rule's network); the fallback (the fill per cell with an always-on warning) is no longer needed for accuracy. *Review (README 10.5): go; the faces' own error on the mapping is 0.2 to 0.7 % on real windows; the network's 1.2 to 1.6 % is a limit of the laminate rule, stated with the import.* The X3 component layer is cheap (one reader, 35 of 35 parts on the sample) and can enter 2.5.0 or 2.6.0. **For 2.6.0 or later:** ODB++ (specification not obtained; reader from memory checked on three archives), IPC-2581 (not read), the KiCad `.kicad_pcb` file (not studied here), lifting the `AB`/`LM`/`LR`/`LS` refusal (no real board uses them), an exposed-pad heat-source shape.

**Branches, in small steps** (each off `develop`, reviewer before each merge, the whole battery):

1. ~~`research/gerber-faces-laminate`~~ done as README 10 of this folder and reviewed (10.5): the default mapping is the faces on the reduced sheet. Owed on the implementation (`feature/imported-copper`): the same split at the program's cells (0.5, 1, 2 mm need a 0.05 or 0.25 mm pixel) on at least one larger window, and a test that the naive order fails.
2. `feature/gerber-reader`: `pcbthermal/gerber/` with the reader, the refusals with file and feature, `TO.C`/`TO.N`/`TO.P` kept apart, the pixel from the thinnest feature and the sample-spacing check, one-byte coverage, layer by layer; conformance tests on synthetic files (the Ucamco files are not committed).

## 10. Re-import (design; the commands are drawn in `prototypes/import_window/`, the diff and the merge are computed for real there)

The question: the project already holds an import (format 2, `imports`) and the user chooses Import again. The window first asks what to do; nothing is written before the answer, and the whole result is **one undo step** of the document.

**What format 2 stores for this** (all of it is in the record of `project_format.import_record`; the prototype adds the last three lines):
* `sources`: per file the **name, size, SHA-256 and function** (never the path). The same set is recognised when the names or the hashes match; a changed file keeps its name and changes its hash.
* `box` (the outline box) and `pix`, to tell a revised board from another board.
* `parts`, **keyed by designator**: position, side, the chosen shape (box or hull, `shape_user` when the user overrode the suggestion), the polygon of the heat source, power, Tj max, role, use. A part picked by hand has an `H<n>` name.
* The manual edits are the fields above; nothing else is needed to merge, because the files give the rest again.

**The three commands** (the dialog says which one it suggests: *update* when the board looks the same and parts changed, else *replace*):
1. **Replace the previous import**: copper, drills and outline come from the new files; a part with the same designator keeps power, Tj max, role, use and a shape the user edited; a part that is not in the new files is listed and **removed only when ticked**, otherwise it stays as an *orphan* (kept, drawn, flagged) so nothing is lost silently.
2. **Update after a layout revision**: the same merge plus the table the user reads before confirming: *moved* (centre shifted by more than 0.3 mm), *resized* (width or height changed by more than 0.2 mm), *new*, *removed*, and what each part keeps.
3. **Add files**: only the functions the import lacks are taken (a drill file, the placement, a second paste layer, a missing copper layer); existing data are untouched. Two files that claim a function the import already has are shown with the hashes as a conflict, one combo each: keep the stored file (default) or use the new one.
4. **Cancel**: nothing changes.

**Results of earlier runs.** They are kept in the project and marked *outdated* (as after any edit); an imported-copper change moves every number, so no result is silently reused. **Undo** restores the previous import, its parts and powers, and the results marked outdated come back as they were.
**A different board.** When the outline box differs by more than 5 % in a side, or no file name and no hash is shared, the dialog says "this looks like a different board" with the reasons and suggests a new project; replacing is still possible (the user may have renamed the files) but the powers of the unmatched parts become orphans.

**Open questions for the maintainer.** (1) Orphans: keep until the user removes them (the prototype), or remove at once after the one confirmation? (2) The move tolerance (0.3 mm) and the resize tolerance (0.2 mm) are guesses: wanted per user or fixed? (3) Parts matched by position only (no `TO.C`) can swap designators when a layout revision moves two parts across each other: accept, or ask for the pick-and-place designators as the key and warn when the paste has none? (4) Should *add* also offer to re-read the placement file against the paste already imported (parts only), as a fourth command? (5) Do results of earlier runs stay in the file (outdated) or are they dropped on a replace?
**Recommendations of the review** (README 11.7; the decisions stay with the maintainer):
1. *Orphans:* keep them until the user removes them, as the prototype does, but **not as heat sources**: an orphan keeps its power and Tj max for a later re-match and is drawn and listed, with `use` off, so that a part that left the layout does not heat a board whose copper changed. A removal after the one confirmation loses typed powers that a renamed designator would have kept.
2. *Tolerances:* fixed, not per user: 0.3 mm (move) and 0.2 mm (resize) are below a 0402 pad pitch and above the 0.05 mm of the paste raster; a 90-degree turn of a part reads "resized" today (width and height swap) and should read "rotated" (compare the sorted sides). One more line in Preferences would add nothing a user can judge.
3. *Parts matched by position only:* use the placement designators as the key (they are the only names the files give), and when the paste has no `TO.C` say so once in the Update table ("designators from the placement file; parts that swapped places are shown as moved"). Accept the swap; do not block.
4. *Re-read the placement:* yes, but as the "Add files" command on a placement file (already its case) and a "Match again" button on step 2, not as a fourth command of the dialog: re-reading changes parts, not the import.
5. *Results of earlier runs:* keep them marked outdated (as after any edit; the undo brings them back).
Two defects of the prototype's merge were fixed by the review (README 11.7, item 4): the user's shape choice is now applied to the new openings (the record carries both shapes), and the diff compares centres in one frame.
Status: design and prototype only; the diff, the merge and the dialog run on the RP2040 board and on a synthetic board (tests in `prototypes/import_window/tests`).


## 11. The matching rule of the parts, the stepper window and the shape (README 11)

**The matching rule to adopt** (replaces "nearest paste group within 0.8 mm, one group per part" of the prototype):
0. **Frame of the placement file first** (review, README 11.4): (a) the bottom-side position convention (X as written or negated, a KiCad option; isastm and cmm2 differ) is detected from the openings (`component_match.bottom_convention`, the convention with more bottom openings inside an envelope; it took isastm from 738 to 744 correct openings and changed nothing elsewhere); (b) a frame check: when the share of SMD parts of the placement file with at least one opening in their envelope falls clearly below the share with the file as given (or many part origins lie off the outline), say that the placement file may use another origin and offer the offset that best aligns the two-pad passives (to be measured on the implementation: the rule tolerates 0.5 mm, loses a quarter of the openings at 1 mm and assigns wrong designators silently at 5 mm); (c) rotations counter-clockwise with Y up (the four boards; the sign matters only off the quarter turns).
1. When the paste file names its parts (`TO.C`), the designator of each opening is the answer (unchanged, README 4.4).
2. Otherwise, per **opening** (link 0.05 mm, no grouping first): the part whose pad envelope, rotated by the part's angle and grown by **0.3 mm**, contains the opening centre; the **smallest envelope wins**; **one part may take many openings**. The envelope of a part comes from its footprint pad extents (the footprint name when no library is read: 0402 to 1206, SOIC pins and pitch, SOT-223, pin headers, the QFN from the paste). Result on the RP2040 board: 18 to 27 of 30 parts, 129 of 129 openings; cmm2 90 to 99 of 101 (453 correct, 9 wrong, 32 missed of 494), isastm 105 to 130 of 134 (738 / 0 / 34 of 772; **133 and 744 / 0 / 28 with the bottom convention of step 0**), oswlight 40 to 43 of 43 (126 / 0 / 80 of 206).
3. The user can always change an assignment (click an opening, Ctrl+click to add, a part's openings listed); the table says "by designator" or "by position" per part, and warns that the paste file names no part.
4. Parts with no opening (through-hole headers, connectors) stay as parts without a heat source, listed, not an error.
Limits to carry into the program: the envelope table must grow (TSOP, USB-C, batteries) or be read from the footprints of the placement file's package column; parts that are in the paste but not in the placement file take no openings (the 9 wrong cmm2 openings were openings of such a part taken by a neighbour: an opening outside every envelope of the placement file, or in the envelope of a part the file does not list, should stay unassigned).

**The window layout (decided): the stepper.** Three numbered steps joined by a line (current in the accent, finished with a check, locked ones muted with a tooltip that says why), Back / Next, Import on step 3, and a secondary *Import now* once step 1 is complete (figure 18); the tab and wizard variants of the prototype are not carried on.

**Re-import (INTEGRATION 10).** Replace, Update and Add files, asked before anything is written, one undo step (figure 19).

**The shape of the heat source.** ~~Suggested: the bounding box of the part's openings, or the hull when it differs from the box by a few per cent.~~ **Review recommendation: the convex hull as the one default**, always editable per part (box, hull, a single opening). Reasons, measured (README 11.5): the box is not the conservative choice, it is never hotter than the hull (the hull is hotter by 0 to 5.2 % of the local rise on the four parts, 0 to 1.3 % of the total on the synthetic board); the hull equals the box for a rectangular pad pattern (U2), follows the pattern of a part turned off the axes (the axis-aligned box of a pad pattern turned by 45 degrees is twice its area for a square pattern and more for an elongated one), and needs no threshold (the prototype's "hull when it covers less than 0.85 of the box" goes away). The openings-only shape is not offered as the default: it is not a bound either way (+11.8 % for the QFN, -12.1 % for the SOIC). For an exposed-pad package (one opening holding most of the paste) the largest opening is the physical entry of the heat and a candidate the step 2 page can propose; that is a separate question for a study with a package model, not settled here.

## 12. Gerber X3 component layer: `feature/x3-components` (README 12)

**What it is for.** A KiCad-written X3 component layer (`Component,L<p>,Top|Bot`) lists every part with reference, footprint, value, mount type, rotation, origin (centroid), an outline and the pins; the paste (`TO.C`) and the copper (`TO.P`) files carry the same references. On the three Ucamco samples (434 parts, 1711 pins) it makes the matching **exact**: all 370 SMD parts meet their paste group by the reference alone, the 64 without paste are the through-hole and `Other` parts, and the pins sit on the copper pads at 0.0 mm. It is **one more source, not the only one**: only KiCad (8.99 on the samples) is known to write it; Altium and EAGLE write X2 only (a third-party guide, low reliability); the placement file plus paste (section 11) stays the main path, and a board without the layer is unchanged.

**What changes in `pcbthermal/` (new branch off `develop` after `feature/gerber-reader` and `feature/project-format-2` are merged; the prototype is `research/gerber-real-boards/lib/x3_components.py`).**

1. `pcbthermal/gerber/components.py` (no GUI, standard library only): `Pin(number, name, x, y, key)`, `Component(ref, side, layer, origin, rotation, footprint, value, mount, height_mm, package, manufacturer, mpn, library, outlines, pins, notes)`; `parse_components(text, name)` and `read_components(path)` (a small tokeniser: extended commands, the current aperture function, the object attributes `.C`, `.P`, `.Cxxx`, G01/G02/G03 with G75 arcs cut at 5 degrees, FS and MO, inch converted, `.CHgt` converted to mm; **the object attributes are a dictionary read when each object is created** (review, README 12.7): the characteristics come from the `ComponentMain` flash whatever their order, an outline belongs to the part of its `.C`, a pin to the part named by the first field of its `.P`, a second `ComponentMain` of one reference is a duplicate, and a change of aperture ends an outline); `duplicate_references`; `to_board`/`to_local` (the rotation rule of README 12.4); `link_paste(components, paste_layer)` and `link_copper(components, copper_layers)` by `TO.C` and `TO.P`, returning for every part the paste openings and the copper pads, the parts without paste (with their mount type) and the references of a layer that no component has. It does not subclass `Layer`: the program's reader keeps `.C`, `.N`, `.P` and ignores the `.Cxxx` and the outline type, and a second small parser for one layer kind is cheaper than widening the raster reader (decision for the executor: extend `Layer` only if `feature/gerber-reader` has not merged). `functions.detect_function` already returns kind `component` (the file function `Component,L<p>,Top|Bot`, and the `pnp_*.gbr` names of KiCad need a check in the name rules: the Ucamco `pnp_top.gbr` is detected by the head).
2. Mapping to the project: `ImportPart(designator=ref, shape, polygon_mm, footprint=.CFtp, side, ...)`. The X3 data that format 2 has no field for (`value`, `mount`, `rotation_deg`, `height_mm`, `package`, `mpn`, `source`) go into `ImportPart.edits` read-only keys until the format adds optional fields (they are forward compatible: unknown keys are kept and written back by `extra`); **the maintainer decides whether to add them as fields of `ImportPart`** (one small change of `model.py` with the tests of `feature/project-format-2`; nothing in a model reads them).
3. The heat-source shape (**proposal, the maintainer decides**; README 12.3): the order **Body, Lead2Lead, the hull of the paste openings linked by `TO.C`, Footprint, Courtyard, hull of the pins**, always editable per part and with the shape name shown. The reason for putting the paste hull before the Footprint and the Courtyard: on the samples the courtyard is 1.57 times the paste box in area (it carries the clearance of the library; a heat source that large cools the part by spreading) and the pins hull 0.23 to 0.65 times (a two-pin part has no area); a body outline, when a tool writes one, is what dissipates and wins. None of the samples has a Body or Lead2Lead outline, so on KiCad files the shape is the paste hull of 4.4/11.5 and the X3 gives the **link**, not a new shape; for a part with no paste (through-hole) the Footprint outline or the Courtyard is offered with the source named, and it is a part without a heat source until the user switches it on.
4. The height (`.CHgt`) is stored and shown (the parts table gets a column); **no model uses it** (the program has no part height; a use for the convection of a tall part is not proposed). Mount type: `SMD` parts are heat-source candidates, `TH`, `Pressfit` and `Other` (and `Fiducial`, the value of files older than revision 2024.05, or any unknown value) are listed without a source and with a tooltip that says why.
5. The import window (parts tab, README 11 and figure 18): a column **Source** with four values in this order of trust: **X3 component layer** (green: exact, no registration, no bottom-sign detection, no envelope table), **paste TO.C + placement file** (blue), **paste + placement by position** (amber, estimated, the rule of 11), **paste only** (grey). Step 2 (files) lists the component layers with their role; a board with both an X3 layer and a placement file uses the X3 layer and shows a note if the two differ (parts in one and not in the other; positions farther than 0.5 mm). The reference of a component layer, a paste layer and a copper layer that disagree (StickHub: C38, J1, JP1 in the copper, not in the component layers) is shown as a warning, not an error. Tooltips, user guide and `tests/test_help.py` words for the new column.

**Tests** (a new `tests/test_gerber_components.py`, the prototype's tests are the base): the synthetic layers of `research/gerber-real-boards/tests/test_x3_components.py` (every outline type, an arc, a height in inches, a bottom part, duplicates, a missing FS), the rotation rule on a footprint at four angles top and bottom, the link of a synthetic paste file and copper file; the Ucamco samples as **skipped-when-absent data tests** (they are not committed: counts 434 / 1711 / 370 linked / 64 without paste, three readers agree); a stress scenario of the import window with an X3 layer; the whole battery. **Risks.** (a) The rotation and bottom rule rests on 35 footprints and 7 bottom/top pairs of one tool; the rule is the specification's, the flip direction is read from the data, so the import must show the rotated outline over the copper and the first release should say so in the documentation. (b) A tool that writes X3 differently (a body outline, a missing `.CRot`, parts in step and repeat) is untested: unknown constructs go into `notes` and fall back to the paste route, never to a silent wrong shape. (c) A component layer lists the assembly; parts left out of it (DNP, StickHub's three) stay in the copper only: the paste route shows them. (d) The sample files' licence is not stated: tests use data that is not committed, the documents quote statistics. (e) The ODB++ and IPC-2581 routes carry height and body (ODB++ `.comp_height` on 199 of 199 parts of the Altium sample, README 4.4 F): the `Component` class is the common target, and the fields (`height_mm`, outlines) are the same.

**Decisions for the maintainer.** (1) The heat-source order of item 3 (the paste hull first, or the X3 outline first). (2) Optional fields of `ImportPart` (item 2) or `edits` only. (3) Whether X3 enters 2.5.0 together with `feature/paste-parts` (it is small: about 250 lines, no new dependency) or after it. (4) Whether the import window offers X3 only when the file function says `Component` or also when a `pnp_*.gbr` has the right head.

**Recommendations of the review (README 12.7).**

1. *Shape order:* **adopt Body, Lead2Lead, paste hull by `TO.C`, Footprint, Courtyard, pin hull.** The drawing of the outline types (specification p. 157) shows that the Footprint outline is the contour of the land pattern, so for an SMD part it is about the paste hull, and the order between them changes little. The courtyard is 1.57 times the paste box in the frame of the part (median of 360 parts, up to 2.39), so it comes last before the pins. This agrees with the hull as the default shape of README 11.7. For a through-hole part, which has no paste, the Footprint outline is the right offer, with the source named.
2. *`ImportPart` fields or `edits`:* **not `edits`.** `ImportPart.edits` is defined as "the user's edits" and survives a re-import (format 2). Values read from a file and stored there would look like user overrides, and they would not be refreshed when the file changes (a new value or rotation in the X3 layer would be shadowed by the old one). `extra` is reserved for keys of a later version. Recommended: **one optional field holding the file data** (for example `from_file: dict` with value, mount, rotation_deg, height_mm, package, mpn, source), rewritten at every import, never merged with `edits`, and written only when not empty, so that format 2 files without X3 stay byte-identical. It is a small change of `model.py` with the round-trip tests of `feature/project-format-2`, and an older 2.5.0 reader keeps the key through `extra`.
3. *With `feature/paste-parts` or after it:* **after it, on its own `feature/x3-components` branch.** The two share the parts tab, `ImportPart` and the matching code, so they cannot be developed in parallel (the rule of the project for branches that share files). X3 is small and can still enter 2.5.0 when `feature/paste-parts` is merged early enough. It should not hold up the release: the placement file and the paste remain the main route, and X3 is written today by KiCad only.
4. *Detection:* **the file function first** (`%TF.FileFunction,Component,...`, which the specification requires of a component layer). **As the fallback, use the content, not the name:** a file without the file function that defines an aperture with `TA.AperFunction,ComponentMain` is a component layer. KiCad's `pnp_*.gbr` name is used only to suggest the role in the file list, never to decide it; a name alone, without `ComponentMain`, is not read as X3.
