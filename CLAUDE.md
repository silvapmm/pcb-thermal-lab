## Project Overview

**PCB Thermal Lab** (see `pcbthermal.__version__`; the original wxPython program was "PCB Thermal Simulator Tool" 1.0.0) is a
physics package, command line and PySide 6 application for simulating the thermal behavior of printed circuit boards (PCBs).

- Author: Pedro Silva (PMS Labs)
- License: MIT, Copyright (c) 2025-2026 Pedro Silva (PMS Labs) (see `LICENSE`).
- Users draw PCB elements (zones, heaters, vias, heatsinks), configure parameters,
  and run three main models (keys `fvm`, `lumped`, `analytic`) plus two comparison models:
  - **Finite volume (FVM), reference**: cell-centred finite volumes on a sparse matrix (direct, CG or SOR solver), any geometry.
  - **Thermal network (LPTN)**: lumped-parameter thermal resistance network per heater (rings by distance from the footprint).
  - **Analytical (Fourier series)**: multilayer cosine series with local corrections for vias and heatsinks.
  - Comparison models (keys `fdm`, `solid3d`): **FDM** (node-centred finite differences of the same layered model, steady state and time) and the **3D solid** (3D finite volumes with real slabs, steady state only).
    The old wxPython solver was also called FDM; it was replaced (see `docs/models.md`, "FDM or FVM").
- Outputs: temperature maps, power profiles in time (square waves and CSV tables), animations, hotspots, gradients, zone and heater
  statistics, reports, CSV and figures. Projects are plain JSON (`.pcbt.json`).

See `README.md` for the full feature list.

## Technology Stack

- Python 3.13 in a virtual environment (`.venv/`, git-ignored): `python3 -m venv .venv && .venv/bin/pip install -r requirements.txt`
- NumPy and SciPy (physics), Matplotlib (figures), PySide 6 (GUI), pytest + pytest-qt + pytest-timeout (tests)
- Always run Python through `.venv/bin/python`; the system Python has none of the dependencies.

## Language and Documentation Rules

These rules are mandatory for all code and documentation in this repository.

1. **Everything is in English**: code, identifiers, comments, docstrings,
   documentation files, and everything git-related (branch names, tag names,
   commit messages, PR titles and descriptions; see "Git Language and Naming").
   (Conversation with the maintainer may be in Portuguese; the repository never is.)
2. **Inline comments** must be present throughout the code, using `#` in Python.
   Explain the *why* and any non-obvious step, not just restate the code.
3. **Doxygen-style documentation** is required for every module, class, function,
   and method. In Python, write it as a docstring using Doxygen commands:

   ```python

       """!
       @brief Solve the steady-state temperature field with the FDM/SOR method.

       @param max_iter   Maximum number of SOR iterations.
       @param omega      SOR relaxation factor (1 < omega < 2).

       @return numpy.ndarray Temperature field in degrees Celsius.
       @throws ValueError If the grid and power map shapes do not match.
       """
       # Validate inputs before starting the iteration
       ...
   ```

   Use at least `@brief`, `@param`, and `@return` (plus `@throws`, `@note`,
   `@see` where useful). Start each file with a `@file` / `@brief` header block.
4. **Licence header on every source, script and configuration file** (maintainer, mandatory, always: 'something that must exist and be a RULE is putting that header, the one that mentions me and the licence, in ALL files'): the first two lines of every `.py` file (after a shebang or an encoding line, if any, and before the module docstring, which stays the first statement) are exactly:

   ```python
   #  Copyright (c) 2026 Pedro Silva (PMS Labs). All rights reserved.
   #  This code is licensed under the MIT License. Inclusion of this notice is required in any redistribution.
   ```

   It applies to `pcbthermal/`, `tests/`, `examples/`, `research/` and `tools/`, to every new file too, and `tests/test_license_header.py` fails for a file without it.

   **The same two sentences, in the comment syntax of the file, are the first lines of every other tracked file that can hold a comment**: shell scripts (after the shebang), HTML (a comment of four lines, `<!--`, the two sentences indented by two spaces, `-->`, right after the `<!DOCTYPE html>` line, which stays first for standards mode), and the files with `#` comments (`.gitignore`, `requirements*.txt`, `.toml`, `.yml`, `.yaml`, `.cfg`, `.ini`, `Makefile`: the same two `#` lines). **Exempt**: data that cannot hold a comment or is read as data (JSON, CSV, images, icons, patches, `tools/ocr/data/prompt.txt`), `LICENSE`, generated outputs, third-party material, the agent instructions in `.claude/`, and the Markdown documents (they carry the 'Author and license' statement of `README.md` and the About box; no header is added to them unless the maintainer asks). A new file of any covered type carries the header from its first commit, and `tests/test_license_header.py` (its list of files is the tracked files) fails naming the files that lack it.
5. Keep the documentation in sync with the code: update docstrings and this file
   whenever behavior changes. `tests/test_docs.py` fails if a module, class, function or method in
   `pcbthermal/` or `examples/` lacks `@brief`, an `@param` per argument, or an `@return` for a returned value.

## Conventions

- Style: follow PEP 8; use type hints on public functions.
- Names: `snake_case` for functions and variables, `PascalCase` for classes,
  `UPPER_CASE` for constants.
- Units: use SI units internally (m, W, K, W/m·K, W/m²·K). Convert only at the
  UI boundary, and state units in the docstring of every parameter.
- Keep solver logic (numerics) separate from GUI code so solvers can be tested
  without wxPython.
- Use the `logging` module instead of `print`.
- Never commit generated outputs (PNG, GIF, TXT reports, temp files); the README screenshots in `docs/images/` are the exception (regenerate with `examples/make_screenshots.py`).

## Git Workflow

- Default branch: `main`; active branch: `develop`. Do not commit features directly
  to `main`; use a branch and open a PR with `gh pr create`.
- **Branch rule** (maintainer, mandatory): every working branch (`fix/<topic>`, `feature/<topic>`, `docs/<topic>` and `research/<topic>`) is created **from `develop`**, right when the work starts, never from `main` or from another working branch. When the work is finished (reviewed, the whole battery green) it is **merged into `develop`** with a merge commit (`git merge --no-ff`, so that the branch stays visible in the history). **Work branches are never deleted, locally or on the remote: they stay as the record of the work**, the same for `research/<topic>`, `feature/<topic>` and `fix/<topic>`. Names are exactly `fix/<topic>`, `feature/<topic>` and `research/<topic>` (kebab-case, English). `main` receives `develop` only when everything planned for the next version is done and the maintainer is satisfied, and that merge is the release (version bump, `CHANGELOG.md`, tag; see "Branches and Versions").
- **Agent worktrees** (maintainer): an agent started with an isolated worktree gets an automatic local branch `worktree-agent-<id>` in `.claude/worktrees/`, never pushed, which has no work of its own: the agent must create its real branch (`fix/<topic>`, `research/<topic>`, ...) **from `develop`** inside it (`worktree.baseRef` is `head` in the settings, so the worktree already starts there). When the agent has finished and its work is merged into `develop`, Claude removes the worktree (`git worktree remove`), checks that no commit exists only on the automatic branch (`git rev-list --count develop..<branch>`) and **deletes the automatic `worktree-agent-*` branch** (`git branch -D`; if a commit exists only on it, Claude reports it and does not delete). These automatic branches are the only branches Claude deletes; the agent's real branch is kept like every work branch.
- All git text is in English (details below).
- The Claude GitHub app is installed on the repository (`/install-github-app`).

### Git Language and Naming

Mandatory, and applies to everything that ends up in the repository history or on GitHub:

- **Language**: branch names, tag names and tag messages, commit subjects and bodies, merge commit
  messages, PR titles, PR descriptions and comments, release notes and issue text are all in **English**.
  Talking to the maintainer in Portuguese does not change this.
- **Branch names**: ASCII, lowercase, kebab-case, with a type prefix: `feature/<topic>`, `fix/<topic>`,
  `docs/<topic>`, for example `feature/component-models`, and `research/<topic>` for studies that do not change the program, for example `research/gerbers`.
  No accents, spaces or Portuguese words.
  The integration branches are `main` and `develop`; every other branch is a work branch, created from `develop`, merged back into it with `--no-ff` and kept as the record (see the branch rule in "Git Workflow").
  **Research branches are merged and kept** (maintainer): a `research/<topic>` branch is opened for one investigation; when the investigation is closed (reviewed, the whole battery green on the merged tree) it is merged into `develop` with `--no-ff` and the branch stays, locally and on the remote, as the record, together with the folder `research/<topic>/` in `develop`. The same holds for every `feature/` and `fix/` branch.
- **Commit messages**: imperative mood ("Add", "Fix", "Remove"), a subject of at most 72 characters
  without a final period, then a blank line and a body that explains *why* when it is not obvious.
  One logical change per commit. Keep the attribution trailers required by the session.
- **Tags**: annotated, `vMAJOR.MINOR.PATCH` (see "Branches and Versions"), with an English message;
  non-release markers use a descriptive English name, for example `legacy-wxpython-1.0.0`.
- **Published history is never rewritten** (no force push). A message that breaks these rules is
  corrected going forward, not by rewriting history.
- Audited on 2026-10-16: all existing branches, tags, commits and the open PR already follow these rules.

## Branches and Versions

- `main`: released versions only, each tagged `vMAJOR.MINOR.PATCH` (annotated tag). - `develop`: integration branch for the next version; every fix, feature, documents and research branch starts from it and merges back into it when finished (see the branch rule in "Git Workflow"); `main` gets `develop` only at a release.
- Tag `legacy-wxpython-1.0.0` marks the original wxPython program (version 1.0.0), kept for reference.
- Version policy: semantic versioning. The only definition of the version is `pcbthermal/__version__` (`pcbthermal/__init__.py`); it is shown in the GUI
  (title bar, status bar, About), in `--version`, in reports and in saved projects. A release needs: version bump, `CHANGELOG.md` entry
  (`tests/test_version.py` checks it and the README), README update, tests green, merge to `main`, annotated tag, push.
- **Frozen numbers** (`tests/regression/`): the test holds the program to the numbers of the last release. At a release, **after the version bump**, run the harness of `research/release-regression-245/` on the previous tag and on the tree (`study_baseline_release.py --tag v<previous>`, `study_run_suite.py --label final`), `study_diff.py ... --strict` (0 alarms; every shift explained by an item of the release, table `expected_shifts_<version>.json`), then `study_freeze_reference.py out/v<previous>.json out/final.json --version <new>` and copy `reference/v<new>.json` to `tests/regression/data/` (the test reads the newest file). A release that changes no number leaves the file as it is and the test must pass; a model change on purpose refreezes in the same commit and says which records moved (`research/release-regression-245/INTEGRATION.md` 2).

- **Reporting**: after each step say briefly what was done, what the numbers are, what was not done or not verified, and which decisions are left to the maintainer.

## Agents and workflow

Maintainer's rule (2026-10-24, extended): the work is done by five project agents in `.claude/agents/` (committed; each file holds its model, effort and instructions). An agent cannot call another, so **the main session orchestrates**: it calls each agent in turn, passes it the previous agent's report, and relays the result to the maintainer.

| Agent | Model, effort | Role |
| :-- | :-- | :-- |
| `researcher` | Sonnet 5.5, medium | Opens and carries an investigation: sources (open archives, the web), questions, study plan, studies, the research folder (README, INTEGRATION.md, docs/, bibliography). Never edits the program. |
| `executor` | Sonnet 5.5, medium | Writes and runs code: study scripts, solvers in `lib/`, figures and diagrams, changes to `pcbthermal/` on a `fix/` or `feature/` branch. Reports the numbers; does not judge them. |
| `reviewer` | Opus 5.5, medium | Independent review: re-reads the code against `docs/theory.md`, re-runs the studies, checks every claim against an independent reference and the printed numbers, finds defects, then corrects the code and the documents. |
| `maintainer` | Sonnet 5.5, medium | Documents, user guide and tooltips that a change touches; diffs; tests and the whole battery; commits, merges and pushes within the Git Policy. Does not change the physics. |
| `tester` | Sonnet 5.5, medium | The local "CI" (there is no remote CI; tests run on the maintainer's machine): the whole battery, the research tests, the reproduction of the numbers of the research READMEs and the frozen reference numbers of a release; finds the cause of every failure or shift; one heavy `pytest` at a time. Does not change the code or the physics, does not merge. |

**Flows** (the reviewer is never skipped):

* **Investigation** (`research/<topic>` branch): `researcher` (with `executor` for large code) -> **`reviewer`** -> fixes by the reviewer, or back to the researcher/executor if the findings need new studies -> `reviewer` again until it is ready -> `maintainer` (research tests, the program-untouched check, commit, push).
* **Change to the program** (a correction, an improvement of an algorithm, a new feature; `fix/` or `feature/` branch off `develop`): `executor` -> **`reviewer`** -> `maintainer` (documents, whole battery, commit, merge into `develop`, push).
* **Closing an investigation, adopting a proposal or any change to a model**: the `reviewer` is called before the merge, with the claims and the numbers to check. **When an investigation is closed the reviewer must review it and update it** (maintainer's rule, mandatory): it re-runs the studies, checks every claim against an independent reference, corrects the folder (README results, the chapter 'Review' with the independent checks, the limits and what was not verified, `INTEGRATION.md` with the recommendation for each decision, the figures, the bibliography statuses), and **updates the registers** (`research/REVIEW.md` row with the status and the program version, `research/README.md` index, `research/ROADMAP.md`), all in the commit of the review, and gives a go or no-go in writing. An investigation without that review is not closed and is not merged. When the program changes later, the reviewer repeats it for the folders that import the program (the reproduction pass of the release).
* **The theory** (`docs/theory.md`): any model change updates it in the same branch (by the `maintainer`, formulas taken from the code, a picture for each section, sources by key with the reading status); the `reviewer` checks the whole document against the code before a release and its verdict is written down.
* **A release** (maintainer's gate, mandatory, in this order): (1) every `fix/`/`feature/` branch of the version is merged, each already through executor -> reviewer -> maintainer with the whole battery; (2) research branches closed and merged (reviewed folders; libraries that read the program updated); (3) the theory and the documents reviewed; (4) **the reproduction pass**: the `tester` re-runs the studies of every research folder that imports the program and the reference numbers on the final tree, compares them with the previous release and with the README numbers, and every shift is linked to an item of the version (differences are fine when a new study explains them; an unexplained one is a defect until proven otherwise); (5) the `reviewer` gives a **final opinion** (go or no-go) on the code (the whole diff against the previous release, including how the changes interact), the program, the documents and the investigations; (6) the whole battery on the final tree, read to its last line; (7) only then the version bump, `CHANGELOG.md`, merge to `main`, annotated tag, push (see "Branches and Versions"); (8) afterwards the finished `worktree-agent-*` worktrees and branches are removed as the settings allow (no commit may exist only on them), and the next version's studies are opened.
* **Preparing the next version**: while a release is being closed, researchers and executors may open `research/<topic>` branches that only **plan and write** (README with numbered studies, INTEGRATION.md, scripts and tests written, nothing run); the runs wait for a quiet machine, after the release.

```
 investigation:  researcher (+executor) -> reviewer -> [fixes / new studies -> reviewer] -> maintainer -> develop
 program change: executor -> reviewer -> maintainer (docs + whole battery) -> develop (--no-ff)
 release:        all branches merged -> theory reviewed -> tester: reproduction + reference numbers
                 -> reviewer: final opinion (code, program, docs, studies) -> whole battery -> main + tag
```

**Two roadmaps, kept apart** (maintainer): `docs/versions.md` (chapter 'Planned') holds only what we want to **implement** in the program (features, corrections of defects, improvements of the models, the interface and the tools), each item once, with a pointer to its evidence; `research/ROADMAP.md` holds only what we want to **investigate** (open questions, measurements to repeat, sources to open, ideas to test), and lives on the research branch with `research/REVIEW.md` (the review register: status of every folder). The review of every research folder is tracked in `research/REVIEW.md` (status, program version of the last run, notes); update it in the commit of each review so that a new session continues from there.

**How the main session orchestrates** (maintainer's standing rules, so that they are not asked again):

* **Parallelism follows the load of the PC** (maintainer's rule: measure the machine and use it; a ceiling may be set, but the real state decides): before launching an agent that runs heavy work, and at every report, the main session measures `uptime` (load average), `sysctl vm.swapusage`, `vm_stat` (free + inactive pages, 16 KB each) and the biggest Python processes. Heavy jobs (a battery, a long study, a big solve) may run **in parallel up to the ceiling of 3 at once** only while the load average is below 5 (10 cores), swap used is below 2.5 GB and has not grown by more than 1.5 GB since the job started (the swap figure of macOS stays high after pressure, so the growth is what counts), and the free + inactive memory is above 6 GB plus the declared peak of the new job; otherwise they wait in series. Above load 8 or swap above 2.5 GB, one job is paused or stopped. Each heavy job declares its expected peak memory when it is launched. Writing, reading and document work is always allowed in parallel (at most 2 reviewers).
* **Series for heavy work, parallel for writing.** (superseded in part by the previous rule: this is the default when the PC is busy.) One heavy job at a time (a battery, a long study, a big solve; 16 GB machine, one `pytest` at a time); several agents may run in parallel only when they just read or write documents, plans and scripts. **At most 2 `reviewer` agents at once.** **Exception, the exhaustive test passes** (maintainer's rule: the reproduction pass of a release, the re-run of the studies of every research folder, a full run of the prepared scripts of a new version): the work is split by folder among **up to 4 `tester` agents in parallel**, **one branch only for the whole pass** (`research/reproduction-<version>`, owned by the first tester); the others work in **detached worktrees** (`git worktree add --detach <path> <branch>`: no branch name of their own), each running **one job at a time** inside its own runner, each commits its part report (`PART-B.md`, `PART-C.md`, ...) in its detached worktree and hands the commit hash to the first tester, who brings it into the pass branch with `git cherry-pick` and puts the part reports into one README with the totals (checked, unchanged, explained, unexplained, not run). **Note the load of the PC**: the main session records `uptime` (load average), the Python processes' CPU and the memory at the start, during (every report) and at the end, and says it in the report; the testers pause their runner when the load average stays above 6 or the free memory gets tight, and one tester is withdrawn if the machine becomes slow. Outside these passes, one heavy job at a time. Branches that share files (`fvm.py`, `fdm.py`, `solid3d.py`, `lumped.py`, `analytic.py`, `checks.py`, `docs/theory.md`) are done one after another and merged in that order; the next one starts from the new `develop`.
* **Every branch** is created from `develop` in an isolated worktree, goes through the flow above, and is merged with `--no-ff`; the branches are kept. **No branch for its own sake** (maintainer's rule, mandatory): a **correction or update of work that already has a branch is made ON that branch** (`research/<topic>`, `fix/<topic>`, `feature/<topic>`, `docs/<topic>`): reopen it (a worktree of the existing branch, `git merge develop` into it first), edit, **recalculate** what changed (re-run the studies, refresh the numbers of the README and of the documents), and merge it again into `develop` with `--no-ff`; the branch keeps the whole story of that topic. A new branch is made only for a **new topic**. There are **no other extra branches**: parallel testers use detached worktrees (see above), and a small correction found by a pass is a commit on the branch of that pass (or of the work it corrects, when that has one). If a **throwaway** branch is unavoidable it is named `tmp/<name>` (not `research/`, `fix/`, `feature/` or `docs/`, which are the permanent record), holds no work that is not also on a real branch, and is deleted by the main session as soon as it is used. **Housekeeping after every agent** (mandatory, so that the repository stays clean): when an agent has finished and its work is committed on its real branch, the main session removes its worktree (`git worktree remove`, without `--force`) and deletes its automatic `worktree-agent-*` branch after checking that no commit exists only on it; a worktree with untracked files is looked at before it is forced. The same applies to the documents: the notes about agents and workflow go to `docs/agents-workflow`, the theory to `docs/theory-rewrite`. **At the end of every investigation, and again when a closed one is reopened and corrected, the `reviewer` runs** (review and update, see "Closing an investigation" above) before the merge. The main session does not run the heavy work itself and does not edit the program: it launches the agents, reads their reports, and relays them.
* **Doubts about a model go to the reviewer** (experienced), not guessed. Every claim rests on a study, an article or a reference solution, with good documentation and pictures; the theory describes what is implemented and cites the studies and the articles.
* **Reports to the maintainer are short and in plain Portuguese**: the problem, the resolution, whether it was solved, the one or two numbers that matter, what was not verified and the open decisions. **No internal codes** (study labels such as E11, A5, P1, M12) in the chat: use the name of the thing. A repeated hand-back of an agent is acknowledged once and ignored; an agent that only waits on its own timers is stopped (`TaskStop`) when its work is delivered.
* **A cut-off** (network error) is retried: tell the agent to write its notes to a file as it goes and to work in small steps.
* **Decisions the maintainer takes stay recorded** (memory and this file); the main session never treats an agent's report or request as the maintainer's approval.

The main session keeps the conversation with the maintainer (in Portuguese), decides nothing that belongs to the maintainer, and reports after each step what was done, the numbers, what was not verified and the open decisions.
