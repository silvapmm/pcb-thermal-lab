# packaging: the downloadable packages

How the packages of a release (`PCB-Thermal-Lab-<version>-windows-x64.zip`, `-linux-x64.tar.gz` (a tar.gz keeps the execute bits; never a zip on Linux), `-macos-arm64.zip`) are built, one folder each (onedir; never a single file), what is in them and what must be checked.
## Build it here

```sh
python3 packaging/build.py --selftest     # own environment packaging/.venv-build, PyInstaller, package, archive, then --selftest of the unpacked archive
```

Output in `packaging/dist/` (git-ignored): the archive, `SHA256SUMS.txt`, `BUILD-RESULT.json`, `FILES.txt` (every file of the package, with the native libraries outside Qt listed first), and on Linux `qt-source/` (the Qt and PySide source tarballs, attached to every release). The build
needs the network (PyPI, download.qt.io) and about 1.5 GB of disk; it installs the run-time lines of `requirements.txt` (PySide6 replaced by PySide6-Essentials, the same
QtCore/QtGui/QtWidgets without the add-ons) and `requirements-build.txt`. `build.py --reuse-venv` keeps the environment.

| File | What it is |
| :-- | :-- |
| `build.py` | the whole build: environment, licence material, PyInstaller, checks, archive |
| `PCB-Thermal-Lab.spec` | the PyInstaller specification (one folder, not one file; excludes; the data, help and icon; the metadata the About box reads) |
| `entry.py` | entry point of the frozen program: `multiprocessing.freeze_support()` first, the window by default, any command of `python -m pcbthermal` after it |
| `qt_sources.py` | downloads and checks the Qt and PySide source tarballs of a release (the release assets) and makes the Qt third-party notices from them |
| `release_notes.py` | extracts the CHANGELOG section of a version and adds the Qt source list and the 'First run' section (macOS Open Anyway, Windows SmartScreen, the glibc requirement, the SHA-256 of each package from `SHA256SUMS.txt`, the pointer to `REPLACING-QT.txt`): the text of the draft release |
| `licenses/Qt/` | the LGPL-3.0 and GPL-3.0 texts (third-party, no header); `licenses/_fallback/` the licence text of a library whose wheel carries none (pyamg); `licenses/_system/` the licence of a native library a Qt wheel bundles from outside Qt (ICU, xcb-util and xkbcommon on Linux) |
| `requirements-build.txt` | PySide6-Essentials, shiboken6 and PyInstaller, pinned EXACTLY (`build.py` fails when the installed versions differ; the three Qt/PySide numbers move together) |
| `check_release.py` | the release job's guard: the three packages carry the same Qt and PySide versions, equal to the attached tarballs; it opens every archive: the documents at the top (`REQUIRED`), the program (and `PCB-Thermal-Lab-cli.exe` on Windows), no member matching `FORBIDDEN`, both contacts of the written offer and no trial TODO text |

The workflow `.github/workflows/build-release.yml` runs `build.py` on Windows, Ubuntu 22.04 and macOS (arm64), runs the packed program's `--selftest` there, and on a tag
`v*` attaches the files to the release: it never creates a public release (if none exists it creates a DRAFT with the CHANGELOG notes), never marks Latest, never uses
generated notes; a pre-release tag (`v2.9.0rc1`, with `__version__` 2.9.0rc1; notes from the Unreleased section when it has no section of its own) makes a draft marked pre-release. The actions are pinned to the commit of an exact release. A push to a branch `build-test/**` builds and self-tests only. It runs no test battery. Executables before 2.9.0 do not exist (no retroactive builds).

## What a package contains (the LGPL checklist, per system)

- [ ] onedir: the Qt libraries are separate files (`_internal/PySide6` on Windows and Linux, `PCB Thermal Lab.app/Contents/Frameworks/PySide6` on macOS)
- [ ] at the top of the archive and inside the program: `LICENSE`, `NOTICE.txt`, `SOURCE-OFFER.txt`, `REPLACING-QT.txt`, `BUILD-INFO.txt`, `licenses/`
- [ ] `licenses/Qt/LGPL-3.0.txt` and `GPL-3.0.txt` (verbatim, byte for byte on every system: `.gitattributes` keeps `packaging/licenses/**` out of the CRLF conversion of a Windows checkout, which had changed the GPL text of the Windows trial package), `licenses/Qt/THIRD-PARTY-NOTICES.txt` (names FreeType with its credit line, libjpeg with the IJG sentence, libpng, zlib, PCRE2, HarfBuzz, double-conversion, MD4C, libtiff, libwebp, Unicode)
- [ ] a folder in `licenses/` for every bundled library (the build fails otherwise) and for PyInstaller (its bootloader is in the program), but not for the build-only tools (altgraph, macholib, setuptools, pyinstaller-hooks-contrib are not in the package); `licenses/Python/` with the PSF `LICENSE.txt` and `INCORPORATED-SOFTWARE.rst` (Doc/license.rst of the exact CPython release: libmpdec, expat, libffi, zlib, mimalloc, HACL*, ...; fetched by the build, which fails without it); on Linux `licenses/ICU/` (the Qt wheel bundles ICU 73, whose source is not in the Qt tarballs; the text is `licenses/_system/ICU/LICENSE`, ICU release-73-2, and the build fails on another ICU major); `licenses/INDEX.txt`
- [ ] every native library has its notice in the package: `check_notices` in `build.py` lists the libraries that are neither Qt nor a wheel's vendored folder (`numpy.libs`, `scipy.libs`, `pillow.libs`, `PIL/.dylibs`: in the wheel's own licence file) nor CPython and what its notices cover (libffi, expat, zlib, mpdec) nor the Microsoft C/C++ run-time (Windows; `licenses/Python/LICENSE.txt` quotes Microsoft's conditions for its Distributable Code) nor ICU (`licenses/_system`); a build with `--release` **stops** when one is left (the workflow passes it on every run, trial branches included; only a local build without the flag prints them and goes on) and `BUILD-RESULT.json` records them (`without_notice`). The section 'Native libraries outside PySide6' of `FILES-<system>.txt` is read for each system too. Trial run of 2.8.0 in Actions: Windows and macOS none; Linux 83, of which 45 are pruned (see the next item) and the 38 that remained are now **left to the system** (the policy of the next item), so a Linux package holds no library without a notice
- [ ] **Linux: the libraries of a Linux desktop are left to the system** (maintainer's policy, `left_to_system` and `SHIPPED_SYSTEM_LIBRARIES` in `build.py`, applied in the spec before the pruning): of the 87 shared libraries at the top of the trial package, 75 are not copied (X11 and the base xcb libraries, GLib/GIO, D-Bus, systemd, libgcrypt, libgpg-error, fontconfig, FreeType, libpng, libstdc++, libgcc_s, zstd, lz4, bz2, lzma, GTK-side leftovers, Kerberos, GNU Readline) and 12 ship: libpython, libffi, libexpat and libz (their notices are CPython's) and the **xcb-util libraries** (`libxcb-cursor`, `-icccm`, `-image`, `-keysyms`, `-render-util`, `-util`) and **libxkbcommon** (with `-x11`), all MIT/X11, which many desktops lack, with their texts in `licenses/_system/xcb-util/` and `licenses/_system/xkbcommon/` (the xcb-util texts are the COPYING files of freedesktop.org's `xorg/lib/libxcb-*` projects; xkbcommon is the LICENSE of 1.4.0, the Ubuntu 22.04 version). Every workflow build (trial or tag) stops if any other library without a notice is left; the program therefore expects a normal Linux desktop (Ubuntu 22.04 or newer, glibc 2.35 or newer) with the system packages below
- [ ] **Linux system packages** (Debian and Ubuntu names, the line the workflow installs for the self-test: `libegl1 libgl1 libxkbcommon0 libx11-xcb1 libxcb-randr0 libxcb-shape0 libxcb-xinerama0 libxcb-xkb1 libxcb-glx0 libxcb-render0 libxcb-shm0 libxcb-sync1 libxcb-xfixes0 libdbus-1-3 libfontconfig1 libglib2.0-0`; a desktop has them all already). Fedora and Arch (names only, NOT tried): Fedora `mesa-libEGL mesa-libGL libxkbcommon libxcb libX11-xcb dbus-libs fontconfig glib2`, Arch `libglvnd libxkbcommon libxcb libx11 dbus fontconfig glib2`. **Two different lists.** What a USER needs is the line above. What the BUILD runner needs is that line PLUS the libraries the package ships (`libxcb-cursor0 libxcb-icccm4 libxcb-image0 libxcb-keysyms1 libxcb-render-util0 libxcb-util1 libxkbcommon-x11-0`), because PyInstaller collects only what is installed on the build machine (the second trial run built a package without them: it could not start, `xcb-cursor0 or libxcb-cursor0 is needed`). Two guards follow: `check_shipped` in `build.py` stops every Linux build (trial or tag) whose package lacks one of `REQUIRED_SHIPPED_LIBRARIES`, naming it; and the workflow, after the build and before the self-test, REMOVES the shipped packages from the runner (after a simulation that must show that apt removes nothing else, such as xvfb) and checks with `ldconfig -p` that they are gone, so the self-test runs on the libraries of the package alone (what only the next CI run can verify: that apt accepts that removal on the ubuntu-22.04 image)
- [ ] **Python is pinned** to `3.13.17` in the workflow (`actions/setup-python`; the same patch release exists for the three systems in the setup-python manifest, 3.13.18 only on Linux); `BUILD-INFO.txt` records the exact Python version and the pip freeze
- [ ] **only the Qt modules on `ALLOWED_QT_MODULES`** in `build.py` (QtCore, QtGui, QtWidgets, which the program imports, QtSvg, and the Linux platform support DBus, XcbQpa, the Wayland client, the EGL integrations and QtOpenGL that they link (Linux)); every other module, the GPL-3-only ones and every add-on of `PySide6_Addons` (Graphs, Charts, DataVisualization, Quick3D, SpatialAudio, HttpServer, Lottie, VirtualKeyboard, NetworkAuth, CanvasPainter, Qml compiler, WebEngine, Multimedia, ...), is reported by `check_qt_modules`: the workflow builds with `--release` every time, trial branches included, so the build stops on one; only a local build without the flag warns; the build installs PySide6-Essentials, which has no add-on, and the spec excludes them as well; `tests/test_packaging.py` checks that the program imports only the three modules). QtNetwork is NOT shipped: nothing links it (it came only with the VNC and TUIO plug-ins, which are dropped, and was left behind on all three systems in the 2.9.0 trial packages, with a dangling symlink on Linux); the spec drops it (`UNUSED_QT_LIBRARIES`) and `check_symlinks` stops a build with a broken symbolic link. A new module that a plug-in pulls in is added to the list only after its licence is read (QtOpenGL: LGPL-3.0, read in the qtbase source)
- [ ] nothing that matches `FORBIDDEN` in `build.py` (the GPL-3-only Qt modules, FFmpeg, QtPdf and its image plug-in, WebEngine, QML and Quick, the TLS plug-ins, `opengl32sw.dll` (Mesa, Windows), the GTK 3 platform theme (Linux) and GNU Readline (GPL-3.0; CPython's `readline` module, excluded in the spec, linked it on Linux)): the build fails if one is there. The spec also drops the plug-ins the program never loads (`UNUSED_PLUGINS`: VNC, TUIO touch, which bring QtNetwork) and, on Linux, every library that no kept binary links any more (`unreferenced_libraries`: dropping the GTK 3 theme had left GTK's own dependencies, cairo, Pango, ATK, GdkPixbuf, GIO and their own dependencies, 38 libraries in the trial package; with QtNetwork and Kerberos, 45 go)
- [ ] the versions agree: `SOURCE-OFFER.txt` = `BUILD-INFO.txt` = Help - About (live) = the tarballs attached to the release (`QT-SOURCE-SHA256.txt`)
- [ ] no EULA text, no encryption, no hash check of the Qt files, no static Qt: nothing may block replacing the Qt files
- [ ] **the Qt and PySide source tarballs are attached to EVERY release** (maintainer's decision; Qt says a link to its own servers is not sufficient): `qtbase`, `qtsvg`, `qtimageformats`, `pyside-setup` and `qtwayland` (Linux), about 76 MB once per release, with `QT-SOURCE-SHA256.txt`, NOT committed to git. There is no mode without them. `python3 packaging/qt_sources.py --qt X --pyside Y --out DIR` downloads and checks them by hand. The release notes list them (`release_notes.py --build-result BUILD-RESULT-linux-x64.json` appends the paragraph; the draft the workflow creates carries it, so the release is never created by hand before the workflow).
- [ ] the release job checked `check_release.py` (the Qt and PySide versions of the three `BUILD-RESULT-*.json` equal each other and the tarballs); after the upload **`gh release view vX.Y.Z --json assets --jq '.assets[].name'` shows the five tarballs and `QT-SOURCE-SHA256.txt`** before the release is called closed
- [ ] no `.qm` file (the Qt translations: English-only program, their source is not attached) and no forbidden file in the package nor inside the `.app`; read the file list of every new build (top two levels, and `find . -name '*.qm'`), because a new PyInstaller hook or PySide version can bring in something the scan does not know
- [ ] **once per system before the first public release** a fresh machine (a VM or a second account without Python): download through a browser, clear Gatekeeper or SmartScreen, unzip, run, solve a board; replace `QtGui` with a REAL swap (the file from a `PySide6_Essentials` wheel of another patch version), on macOS re-sign as `REPLACING-QT.txt` says, run again; Help - About shows the Qt version that was loaded; `--selftest` exits 0

## Linux: which systems the package runs on

The Linux package is built on Ubuntu 22.04, so it **needs glibc 2.35 or newer (Ubuntu 22.04+, Debian 12+, Fedora 36+); older distributions (Ubuntu 20.04, Debian 11, RHEL/Rocky 8-9) are not supported by this package: run from source with pip instead.** (PyInstaller's bootloader is not the limit; the bundled libpython and the Qt libraries are linked on the build machine, and TagStudio issue 386 is the live example of the same message on RHEL 9.)

### Design note (nothing of it is implemented): build the Linux package in a glibc 2.28 container

Idea: run the Linux job in a `quay.io/pypa/manylinux_2_28_x86_64` (AlmaLinux 8, glibc 2.28) or `almalinux:8` container instead of `ubuntu-22.04`, so that the package runs on every distribution from about 2019 on (RHEL, Rocky and Alma 8 and 9, Debian 10 and up, Ubuntu 20.04 and up). The Qt 6.12 wheels are themselves manylinux_2_28, so the Qt libraries are not the obstacle; the Python interpreter and the build tools are.

| Point | Cost or risk |
| :-- | :-- |
| Python 3.13.17 | manylinux images carry CPython under `/opt/python/cp313-cp313` at the release the image was built with (from the maintainers' general knowledge, not checked against the image), not at an exact pin; the pin would need `python-build-standalone` or a build from source in the job (minutes, and it has to be a shared-library build, `--enable-shared`, because the bootloader opens libpython), and `actions/setup-python` serves Ubuntu builds of Python, so it would not be used in that container. Risk: medium; availability of exactly 3.13.17 there is NOT checked. |
| Which libraries the package ships | The policy (`left_to_system`, `SHIPPED_SYSTEM_LIBRARIES`) was written for Ubuntu's names and versions; on AlmaLinux 8 the xcb-util libraries (above all `xcb-util-cursor`) and a libxkbcommon with the x11 part probably come from EPEL or must be built (NOT checked which of them the base repositories carry), each with its own licence text under `packaging/licenses/_system/` (the xkbcommon text there is for 1.4.0, Ubuntu 22.04's). Risk: medium to high. |
| apt names against dnf names | The workflow's `apt-get install`, the simulation and the removal of the shipped packages before the self-test become `dnf install` and `dnf remove`; the names differ (`libxcb`, `xcb-util-cursor`, `libxkbcommon-x11`, `mesa-libEGL`, `fontconfig`, `glib2`, `dbus-libs`) and the README lists would need a second set. Cost: small, but every name has to be tried once. |
| The xvfb self-test | The self-test needs a virtual X server (`xorg-x11-server-Xvfb` in the container or, better, a second job that runs the unpacked package on a plain `ubuntu-22.04` and on a Rocky 8 container: that also proves the claim of the package). The Qt xcb plug-in needs the shipped xcb-util libraries and libxcb 1.13 or newer on the system. Cost: a new job and a second run. |
| The Qt xcb libraries | The Qt 6.12 xcb plug-in wants `libxcb-cursor`, `libxkbcommon-x11` and libxcb-xkb; the shipped ones would be built against glibc 2.28 and must work with the libxcb of the user's system (the oldest target, RHEL 8, has an older libxcb than Ubuntu 22.04; not tried). Risk: low to medium. |
| Other | GitHub's JavaScript actions (checkout, upload-artifact) run inside a job container only when the image can run the runner's Node build (whether that holds on glibc 2.28 for the pinned action versions is NOT checked); the build time grows by the Python build; every Linux pin is reproduced again. |

Recommendation: **not now.** Ship 2.9.0 with the stated requirement (glibc 2.35 or newer), because the package, the source offer and the licence checklist are settled for Ubuntu 22.04 and a change of build image reopens the system-library policy (names, versions, texts of the shipped libraries) and the Python pin at once. If a user on RHEL, Rocky, Debian 11 or Ubuntu 20.04 asks, do it as a separate step after the first release: first try the build in `almalinux:8` by hand on a Linux machine (Python 3.13 from the manylinux image, EPEL for the xcb-util libraries), run the unpacked package in a Rocky 8 container, and only then change the workflow; keep the Ubuntu 22.04 job running next to it for one release. Until then the sentence above is the answer.

## Rules for releases (never broken)

Also never (they would close the replacement of the Qt files that the LGPL-3.0 asks for): **never add an EULA that forbids reverse engineering**, **never check Qt file hashes at run time** (no integrity check that refuses a replaced Qt library), **never switch to onefile** (a single packed file cannot have its Qt libraries swapped), never link Qt statically, never ship a Qt module that is not on `ALLOWED_QT_MODULES`.

Never delete a release, never remove one of its assets, never move or re-push its tag to other code, and never publish a package before the source assets are attached (the workflow only creates a DRAFT and uploads the source before the packages; the release is made public with `gh release edit vX.Y.Z --draft=false --latest` after `gh release view` shows the tarballs, never created by hand before the workflow). `SHA256SUMS.txt` on the release lists the packages and the tarballs by their flat names (`sha256sum -c SHA256SUMS.txt` in the download folder). The written offer runs three years and depends on the files staying there.

## Unsigned packages

macOS and Windows packages are UNSIGNED (macOS: ad hoc only, which Apple silicon requires). The README Download section explains Gatekeeper (System Settings, Privacy & Security, Open Anyway, which since macOS 15 replaces the right click, Open of older systems (Apple, "Updates to runtime protection in macOS Sequoia", and the Mac User Guide "Open a Mac app from an unknown developer"); or `xattr -dr com.apple.quarantine "PCB Thermal Lab.app"`) and SmartScreen (More info, Run anyway). `THIRD-PARTY-NOTICES.txt` is made from all the Qt modules' attribution files, so it is over-inclusive (the Qt attribution data does not say which component ends in which library); it lists every component of qtbase, qtsvg, qtimageformats and qtwayland, with the licence texts, and says so in its heading.

## Signing (constraint for later)

The hardened-runtime constraint, recorded for the future. **If a Developer ID and the hardened runtime are ever used** (needed for notarisation), library
validation would block a Qt library built by the user unless the entitlement `com.apple.security.cs.disable-library-validation` is kept, or `REPLACING-QT.txt` tells
users to re-sign the whole app ad hoc. Do not sign in a way that stops the replacement of the Qt files.
